## Private firewall manifest

`node --test deployment/appengine-test/firewall.test.cjs` tests synthetic documentation addresses only. `firewall.cjs` exports `firewallManifest(addresses)` for a nonempty array of exact IPv4 strings. Each becomes a priority-1000+ `/32` ALLOW, followed by priority-2147483647 `*` DENY, including unmatched IPv4 **and IPv6**. Empty, malformed, CIDR, wildcard, duplicate and IPv6 allowlists refuse generation. Under the retrieved official API discovery contract, omitting the final wildcard causes batchUpdate to append ALLOW ALL, so the explicit final DENY is essential.

For private generation only: `node deployment/appengine-test/firewall.cjs /private/path/allowed-ipv4.txt /private/path/firewall.json`. Both files must be outside the checkout; use one exact IPv4 per input line. The output parent must already exist; canonical paths are checked. Input symlinks and existing output paths (including symlinks) are refused. Output is created exclusively with mode 0600; stdout contains only a fixed success message and address count, never the manifest or paths. Do not print the resulting manifest, commit it, include it in upload staging, or attach it to an issue. Generation does not apply anything. Proposed API review target: `POST https://appengine.googleapis.com/v1/apps/{appsId}/firewall/ingressRules:batchUpdate` with generated body `{ "ingressRules": [...] }`. This atomically replaces the **entire** ruleset; preserve/review any existing rules first. Never publish versions before deny-by-default firewall enforcement is established and independently verified.

Consult current official [deployment roles](https://cloud.google.com/appengine/docs/standard/roles), [firewall API](https://cloud.google.com/appengine/docs/admin-api/reference/rest/v1/apps.firewall.ingressRules/batchUpdate), [firewall behavior](https://cloud.google.com/appengine/docs/standard/creating-firewalls), runtime support and billing documentation. One public IP identifies network egress rather than a device: shared Wi-Fi users share access, mobile/VPN/IPv6/dynamic-IP changes can block expected devices. Never substitute an agent/proxy address for the user's network IP.

## Access check verified 2026-10-30

The updated network policy now permits official documentation and service requests. App Engine application inspection returns IAM_PERMISSION_DENIED; the current identity still has none of the checked deployment permissions. IAM predefined-role lookup also reports SERVICE_DISABLED, so role requirements were verified against the current official App Engine roles page, not inferred from the inaccessible lookup.

The documented deployment roles are **App Engine Admin**, **Service Account User** on the assigned runtime account, **Cloud Build Editor**, and **Storage Object Admin**. Initial application creation separately needs **App Engine Creator**. **Service Usage Admin** is needed for the requested API enablement work. Existing Firebase roles remain needed for the unchanged backend. This records required capability categories; it does not grant them or claim all platform-managed build identities have already been configured.

Official firewall behavior states that the firewall checks regular App Engine requests, including the default hostname, and documents platform-internal warmup/Cron/Tasks exceptions. No such task/cron configuration is proposed. The firewall sits behind caches, so install the deny-by-default rules before first content publication and retain zero-expiration/no-store settings; actual denied-network cache/asset checks are still mandatory. No external IP access is considered active until deployed validation succeeds.
